# iced-x86 C++ port: design and conventions

This document is the contract for everyone working on the C++ port. The C++ code is a port of the **Rust**
crate (`src/rust/iced-x86`). When in doubt, do what the Rust code does.

## Goals

- Full feature parity with the Rust crate: decoder, encoder, block encoder, op code info, instruction info,
  gas/intel/masm/nasm/fast formatters, code assembler.
- Runtime performance similar to Rust (same algorithms, same data layout, same table-driven design).
- Usable on embedded devices: CRT exists but **stack size is limited**.
- All tests that the Rust crate runs (shared test data in `src/UnitTests/Intel`) must also run and pass in C++.

## Language / build rules

- C++17, no compiler extensions required. Must compile warning-free with GCC and Clang (`-Wall -Wextra -Wshadow=local`), should compile with MSVC.
- The library must compile with `-fno-exceptions -fno-rtti` (CMake option `ICED_X86_NO_EXCEPTIONS_RTTI`, used by
  `build/build-cpp`; it's `OFF` by default so the library uses the same flags as the rest of the program). No `throw`, `try`,
  `dynamic_cast`, `typeid`. Errors are returned with `iced_x86::Result<T>` / `iced_x86::IcedError` (`include/iced_x86/iced_error.hpp`),
  which mirror Rust's `Result<T, IcedError>`. Where Rust panics (`iced_assert!`, `unreachable!`, index out of bounds on
  internal tables) use `ICED_ASSERT(x)`, `ICED_UNREACHABLE()`, `ICED_DEBUG_ASSERT(x)` from `src/internal/iced_assert.hpp`.
- **Stack**: no recursion, no VLAs/`alloca`, no big local arrays or big structs on the stack. The build warns if a frame
  is larger than 1024 bytes (`-Wframe-larger-than=1024`); fix any such warning. Big tables are `static const` data.
- **No dynamic initialization, no RAM tables**: no global objects with constructors, no static registration, no lazily
  created tables. Tables that Rust creates at runtime (`lazy_static!`, eg. the decoder's handlers, the encoder's op code
  handlers, `OpCodeInfo`s and all formatter tables) are generated as **constant data** instead (constant initialized,
  in `.rodata`: no heap memory, no startup code, no locks), eg. the decoder tables (see *Decoder tables* below), the
  encoder's op code handlers and the `OpCodeInfo` table (incl. its strings, generated by `CppEncoderGenerator`:
  `src/encoder/op_code_handlers_table.cpp`, `src/encoder/op_code_info_table.cpp`) and the gas/intel/masm/nasm/fast
  formatter tables (see *Formatter tables* below). Such tables are `constexpr` or marked `ICED_CONSTINIT`
  (`internal/encoder/const_init.hpp`) so the compiler verifies that they're constant initialized. The library has no
  `.bss`/`.data` tables and no function-local statics; keep it that way (check with `nm` / `objdump -h`: no
  `.init_array`, no "guard variable" symbols).
- Heap usage: std::string/std::vector are allowed (Rust uses `String`/`Vec` in the same places). Don't allocate in hot
  paths where Rust doesn't (eg. the decoder never allocates, the formatter only appends to the output). Exception: the
  fast formatter never allocates and doesn't use `std::string`/`std::vector` (it formats to a caller provided buffer).
- The library is a static library; the linker only pulls in the object files that are used, so keep each component in
  its own `.cpp` files so eg. an app that only decodes doesn't link the formatters.
- Use `std::uint32_t` etc. (`<cstdint>`), `std::size_t`. Use `std::string_view` for non-owning strings passed to/from the API.
- Formatting: tabs for indentation (like the Rust/C# code), `{` on the same line.
- Don't use `<iostream>` in the library.

## Directory layout (`src/cpp/iced-x86`)

```
CMakeLists.txt               GLOB_RECURSE picks up all src/**/*.cpp and tests/**/*.cpp automatically
include/iced_x86/*.hpp       Public API (namespace iced_x86). Generated enums + hand written headers.
include/iced_x86/code_asm/   Public code assembler API (namespace iced_x86::code_asm)
src/*.cpp                    Core (Instruction, Register/Code/MemorySize helpers, ...)
src/<component>/*.cpp        Components: decoder, encoder, block_encoder, info, formatter, formatter/{gas,intel,masm,nasm,fast}, code_asm
src/generated/               Generated .cpp files that don't belong to a component (eg. enum_names.cpp)
src/internal/**/*.hpp        Internal headers (namespace iced_x86::internal[::gas|intel|masm|nasm|fast]).
                             Generated internal enums also live here, eg. src/internal/decoder/op_size.hpp
tests/                       Unit tests (namespace iced_x86::tests), one sub dir per component: tests/decoder/...
tests/generated/             Generated test files
bench/                       Benchmarks
```

Include paths: `include/` (public: `#include "iced_x86/instruction.hpp"`) and `src/` (internal:
`#include "internal/decoder/op_size.hpp"`). Tests also have `tests/` in the include path.

Generated files start with `// ⚠️This file was generated by GENERATOR!🦹‍♂️` and must never be edited by hand; change
the generator instead. Hand written files may contain generated regions (`// GENERATOR-BEGIN: Id` ...
`// GENERATOR-END: Id`) written by `FileUpdater`, same as the other languages. Prefer whole generated files.

## Generator

The generator is `src/csharp/Intel/Generator` (C#, .NET 10: `~/.dotnet/dotnet`). C++ support: `TargetLanguage.Cpp`,
`CppConstants` (paths/helpers), `CppIdentifierConverter`, `Documentation/Cpp/*`, `Constants/Cpp/*`, `Enums/Cpp/*`.
Put new C++ generators next to the Rust ones in a `Cpp` sub dir (eg. `Decoder/Cpp/CppDecoderTableGenerator.cs`) and
mark them with `[Generator(TargetLanguage.Cpp)]` (they're discovered by reflection). Usually the Rust generator is the
best starting point: the serialized tables are language independent, only the syntax differs.

```sh
cd src/csharp/Intel/Generator
~/.dotnet/dotnet run -c Release -- -l cpp     # only generate C++ files
~/.dotnet/dotnet run -c Release               # all languages: must not change any non-C++ file (check with git status)
```

`CppEnumsGenerator` generates *all* enums (also the ones generated by other generators, eg. the encoder/instr info
generators create a `CppEnumsGenerator` and call `Generate(enumType)`). `GetIncludePath(typeId)` returns an enum's include path.

## Naming (mirror the Rust API)

| Rust | C++ |
|------|-----|
| `enum Code { Add_rm8_r8, .. }` | `enum class Code : std::uint16_t { Add_rm8_r8 = 5, .. }` (generated) |
| `struct DecoderOptions; impl DecoderOptions { pub const NONE: u32 }` (flags) | `struct DecoderOptions { static constexpr std::uint32_t NONE = 0; };` (generated) |
| `Debug`/`Display` of a public enum | `const char* to_string(Code)` (generated, `src/generated/enum_names.cpp`) |
| `IcedConstants::CODE_ENUM_COUNT` | `iced_x86::IcedConstants::CODE_ENUM_COUNT` (public, generated) |
| struct `Instruction`, `Decoder`, `Encoder`, `BlockEncoder`, `InstructionInfoFactory`, `OpCodeInfo`, `GasFormatter`, `FormatterOptions`, ... | same type names (PascalCase) |
| method `instr.op0_kind()`, `instr.set_op0_kind(k)` | same names, snake_case: `instr.op0_kind()`, `instr.set_op0_kind(k)` |
| associated fn `Decoder::with_ip(..)`, `Instruction::with2(..)` | `static` member function with the same name |
| methods on enums: `reg.size()`, `code.mnemonic()`, `mem_size.info()`, `cc.xxx()` | free functions in a `<snake_type>_ext` namespace: `register_ext::size(reg)`, `code_ext::mnemonic(code)`, `memory_size_ext::info(ms)` (header: `include/iced_x86/<snake_type>_ext.hpp`) |
| `pub(crate)` items | `iced_x86::internal` (in `src/internal/**`) |
| `Result<T, IcedError>` | `iced_x86::Result<T>` (`is_ok()`, `value()`, `*result`, `result->x`, `error()`) |
| `Option<T>` | `std::optional<T>` (or a pointer for optional references) |
| `&[u8]` | `const std::uint8_t* data, std::size_t size` (+ convenience overloads: `std::vector<std::uint8_t>`, `std::initializer_list` if the data is copied, C arrays (`template <std::size_t N>`), ...; if the data isn't copied (`Decoder`), temporaries must be rejected with deleted overloads) |
| returned `&'static [T]` (eg. `cpuid_features()`) | `iced_x86::Slice<T>` (`include/iced_x86/slice.hpp`) |
| `&str` / `String` | `std::string_view` / `std::string` |
| trait objects (`Box<dyn SymbolResolver>`, `dyn FormatterOutput`) | abstract classes with virtual functions |
| `impl Iterator` | C++ iterators (`begin()`/`end()`) where it makes sense |
| C++ keyword clash (`and`, `or`, `not`, `xor`, `int`, `default`, ...) | append `_`: `and_`, `int_` (same as `CppIdentifierConverter.Escape`) |

Where Rust uses generic `with2<T, U>(code, op0: T, op1: U)` taking `Register`/`i32`/`u32`/`i64`/`u64`/`MemoryOperand`,
C++ uses overloads with the same name.

**Integer overloads**: an overload set taking `std::int32_t`/`std::uint32_t`/`std::int64_t`/`std::uint64_t` is ambiguous for
other integer types, eg. `0x1234ULL`/`-1LL` (`long long`) if `std::int64_t` is `long` (Linux 64-bit) or `long`/`std::size_t` if
it's `long long` (Windows, macOS). Such overload sets (`Instruction::with1()`..`with5()`, the `CodeAssembler` instruction methods)
also get one forwarding template, constrained with `internal::EnableIfOtherIntArgs<Args...>` (`iced_x86/internal/int_arg.hpp`),
that converts each such arg with `internal::int_arg()` to the exact type with the same size and signedness and calls the
non-template overload. It's only enabled if at least one arg isn't an exact type (and isn't promoted to `int`), so it never
changes which overload normal calls pick.

## Public headers

Public headers (`include/**`) can't include internal headers (`src/internal/**`, not installed). Use `assert()`
(`<cassert>`) for debug asserts in inline public code and `std::abort()` instead of `ICED_ASSERT()`.
Internal tables used by inline public functions are declared `extern` in the public header in `namespace iced_x86::internal`.

## Instruction

`Instruction` (include/iced_x86/instruction.hpp) has exactly the same layout as Rust's (40 bytes, same fields, same
bit packing in `flags1`, etc.). Its data members are private; internal code that needs raw access uses
`iced_x86::internal::InstructionInternal` (a `friend` struct with static functions, the equivalent of Rust's
`instruction_internal.rs`, in `src/internal/instruction_internal.hpp`). Hot getters/setters are inline in the header.

## Decoder

`Decoder` (include/iced_x86/decoder.hpp): `Decoder(bitness, data, size, options)` (Rust `new`), `Decoder::with_ip(bitness, data, size, ip, options)`,
`Decoder::try_new(...)`/`try_with_ip(...)` return `Result<Decoder>`; `std::vector<std::uint8_t>`, C array and `std::array` overloads
exist, eg. `Decoder(64, bytes, options)` (the decoder never owns/copies the data so rvalues/braced lists are rejected by deleted overloads). `decode()`, `decode_out(Instruction&)`, `for (const Instruction& instr : decoder)` (range-for, decodes into the
iterator's instruction). Decoder test cases (used by the encoder/formatter/instr info tests): `tests/test_utils/decoder_test_utils.hpp`
(`decoder_tests(include_other_tests, include_invalid)`, `encoder_tests(...)`, `get_test_cases(bitness)`, `create_decoder(...)`, ...).
Rust `#[should_panic]` tests: `aborts([] { ... })` in `tests/test_utils/abort_utils.hpp`.

### Decoder tables

Rust creates the decoder's op code handlers at runtime (`lazy_static!`): it deserializes the generated byte tables
(`table_de/*_reader.rs`) and boxes each handler (several hundred KB of heap memory). In C++ all
handlers and tables are **constant data** (`constexpr`, no heap, no startup code, no locks; `.rodata`, or `.data.rel.ro`
if compiled with `-fPIC` since they contain pointers):

- `CppDecoderTableGenerator` + `CppDecoderTableWriter` (`src/csharp/Intel/Generator/Decoder/Cpp`) walk the generator's handler
  definitions (`DecoderTable_{Legacy,VEX,EVEX,XOP,MVEX}.cs`: `[kind, args...]` arrays, the same data the other languages
  serialize) and write `src/decoder/data_{legacy,vex,evex,xop,mvex}.cpp` (one TU per table, ~0.3 s each to compile):
  one `constexpr auto Hn = <encoding>_ctors::<Kind>(args...);` per handler (nested handlers first, identical handlers are
  only created once: ~7900 handlers) and the top level 0x100-entry `HandlerEntry` tables (`HANDLERS_MAP0`, `HANDLERS_0F`,
  ..., declared in the generated `src/internal/decoder/data_*.hpp`). `DECODER_TABLES` (`src/decoder/tables.cpp`) has the
  table pointers (+ `INVALID_MAP`).
- Args: enum values (`Code::X`, `Register::X`, `TupleType::X`, `DecoderOptions::X | ...`, `HandlerFlags::X`,
  `LegacyHandlerFlags::X`), bools, ints, `&Hn` (other handlers) and braced lists of handler pointers (named handler arrays,
  eg. a `Group`'s 8 handlers or an `AnotherTable`'s 0x100 handlers). All `Code` values of a definition are passed (the
  serializers only store the first one of consecutive `Code`s).
- The `Invalid`, `Invalid_NoModRM` and `Null` kinds (and `null`) are the singletons `INVALID_HANDLER`,
  `INVALID_NO_MODRM_HANDLER` and `NULL_HANDLER` (`inline constexpr` variables in `handlers.hpp`: one address in the whole
  program, `is_null_instance_handler()` compares addresses).
- The factory fns (Rust's `*_reader.rs` `match` arms) are in `src/internal/decoder/{legacy,vex,evex,mvex}_ctors.hpp`
  (XOP uses `vex_ctors`): one `constexpr` fn per handler kind with the same name as the kind that calls the handler's
  `constexpr` ctor, eg. `constexpr OpCodeHandler_Ev_Gv Ev_Gv_3b(Code code1, Code code2) noexcept { return OpCodeHandler_Ev_Gv{code1, code2, Code::INVALID}; }`.
  The legacy `Simple` kind returns `OpCodeHandler_Simple::int3()` (Rust's `OpCodeHandler_Int3`) if the code is `Int3`.
- All handler ctors are `constexpr` (handlers are literal types). Array args are `const OpCodeHandler* const (&)[N]`
  (too many elements don't compile, a missing element is null which fails `copy_handlers()`'s `ICED_ASSERT`). The
  `ICED_ASSERT`s (and `ICED_DEBUG_ASSERT`s if `NDEBUG` isn't defined) in the ctors are evaluated at compile time: a failed
  assert is a compile error. Ctors can read other handlers (eg. `->has_modrm`) since they're `constexpr` objects in the
  same TU, but they can't use non-`constexpr` tables (the MVEX handlers check `get_mvex_info()` in their decode fns).
- To add a handler kind: add the kind + its handler definitions to the generator (like the other languages), add the
  handler struct (`constexpr` ctor) + its decode fn and a factory fn with the kind's name to `*_ctors.hpp`.
- GCC (x86) aligns objects >= 32 bytes to 32 bytes; `data_*.cpp` are compiled with `-malign-data=abi` (CMake) to save ~37 KB.
- Size: ~330 KB (x86-64) of constant data. A PIE executable needs one relocation per pointer (~32000, 780 KB of `.rela.dyn`
  on x86-64 unless linked with `-z pack-relative-relocs`); embedded (non-PIC) builds don't.

### Decoder performance

Decoder performance notes (keep these when changing the decoder, measure with `perf stat -e cycles:u`):

- The hot part of `decode_out()` (`DecoderCore::decode_out_inline()`: state reset, first byte/REX prefix, table dispatch,
  length/IP/RIP-relative fixups) is inline in `decoder.hpp` and force-inlined into the caller's loop
  (`ICED_X86_INTERNAL_HOT_INLINE`, `iced_x86/internal/macros.hpp`; not forced with `-Os`), which is what Rust gets with
  LTO. Only the table dispatch is inline, the handlers are out of line; rarely used code (invalid instructions, `LOCK`,
  `IP_REL32`) is in `decode_out_slow()` (`src/decoder/decoder.cpp`). `read_u8()`, `read_modrm()` and `decode_table2()`
  are also defined in `decoder.hpp`. That code can't include internal headers so it uses copies of the `StateFlags`
  (`DecoderCore::SF_*`, verified by `static_assert`s in `decoder_core.hpp`) and `DecoderCore` is a `friend` of `Instruction`.
- The 0x100-entry tables and `OpCodeHandler_AnotherTable`/`OpCodeHandler_Group` store `HandlerEntry`s
  (`{decode fn, handler}`, Rust's `(OpCodeHandlerDecodeFn, &OpCodeHandler)` tuples) so the indirect call target doesn't
  depend on a load from the handler.
- Handler decode fns are `noexcept` (`OpCodeHandlerDecodeFn` is a `noexcept` fn pointer): a `noexcept` function calling a
  potentially throwing fn pointer needs an EH region, which prevents tail calls (GCC).
- The hot `DecoderCore` fields (`state`, `data_ptr`, `max_data_ptr`, ...) are first so most accesses need only an 8-bit
  displacement.
- GCC's SLP vectorizer (`-O3`) merges the `modrm`/`mod_`/`reg`/`rm` stores into SIMD shuffles + a 16-byte store which is
  slower: `src/decoder/*.cpp` are compiled with `-fno-tree-slp-vectorize` (CMake) and `read_modrm()` (inlined into the
  user's code) has an empty `asm` that prevents it.

## Code assembler

`iced_x86::code_asm` (`include/iced_x86/code_asm.hpp`). `CodeAssembler a(64);` (or `CodeAssembler::create(64)` -> `Result`).
Instruction methods are overloads (Rust traits/generics), C++ keywords get a `_` suffix (`a.xor_(rcx, rdx)`, `a.int_(3)`).
Instruction/prefix/label/data methods return `CodeAssembler&` and errors are *sticky*: the first error is stored
(`has_error()`, `error()`, `clear_error()`), later calls are ignored and `assemble()`/`assemble_options()` fail with it.
Methods that return a value in Rust return `Result<T>` (`bwd()`, `fwd()`, `CodeAssemblerResult::label_ip()`).
Registers are `constexpr` constants (`rax`, `xmm0.k1().z()`), memory operands: `dword_ptr(rax + rcx * 4 + 8).fs()`.
The generated instruction methods are declared in several base classes (`code_assembler_fns.hpp`, GCC is quadratic in the
number of class members) and implemented in `src/code_asm/fn_asm_impl_N.cpp`. Integer args: see *Integer overloads* above; there's
also a generated inline `mov(AsmRegister64, std::int32_t/std::uint32_t)` overload (only 64-bit immediates exist) so `a.mov(rax, 5)` compiles.

## Formatters

Rust `formatter/**` is split like this:

| What | Where |
|------|-------|
| `Formatter` (abstract class, Rust trait), `FormatterOutput` + `StringFormatterOutput` (Rust `impl FormatterOutput for String`) | `include/iced_x86/formatter.hpp`, `formatter_output.hpp` |
| `FormatterOptions`, `FormatterOperandOptions`, `NumberFormattingOptions`, `FormatterOptionsProvider` | `include/iced_x86/formatter_options.hpp` |
| `SymbolResolver`, `SymbolResult`, `SymResTextInfo`, `SymResTextPart`, `SymResString` | `include/iced_x86/symbol_resolver.hpp` |
| Fast formatter: `SpecializedFormatter<TraitOptions>`, `FastFormatter`, `FastFormatterOptions`, trait options | `include/iced_x86/fast_formatter.hpp`, `fast_formatter_options.hpp` (+ `include/iced_x86/internal/fast_fmt.hpp`, `src/formatter/fast/*`) |
| Shared runtime (Rust `mod.rs` private items, `fmt_consts.rs`, `fmt_utils*.rs`, `num_fmt.rs`, `pseudo_ops.rs`, `regs_tbl_ls.rs`) | `src/internal/formatter/*.hpp` + `src/formatter/*.cpp` (namespace `iced_x86::internal`) |
| Generated data (Rust `fmt_data.rs`, `strings_data.rs`, `regs_tbl.rs`, `mem_size_tbl.rs` regions) | see *Generated formatter data* below |

API notes:

- Rust methods returning `&str` (`format_register()`, `format_i8()`, ...) return `std::string_view`; it's valid until the next call.
- Every `FormatterOutput&` method of `Formatter` also has a `std::string&` overload (appends to the string). Derived classes must add
  `ICED_X86_FORMATTER_USING_BASE_METHODS;` (defined in `formatter.hpp`) to their public section or the overloads get hidden.
  `format(const Instruction&, std::string&)` is virtual: the gas/intel/masm/nasm formatters override it. Their formatter code is a template
  (`XxxFormatterImpl<TOutput>`) that is also instantiated with `internal::BufferedStringOutput` (`buffered_string_output.hpp`, a final
  class): all writes are inlined and copy the text to a char buffer owned by the formatter, and it's appended to the string with one
  `append()` call (Rust gets the same result with LTO; libstdc++'s `append()` isn't inlined). It's 10-15% faster. CMake option
  `ICED_X86_FORMATTER_STRING_SPECIALIZATION=OFF` (defines `ICED_X86_NO_FORMATTER_STRING_SPECIALIZATION`) removes the second instantiation
  (~20 KB less code per formatter), the `std::string&` overload then uses `StringFormatterOutput` + the generic code.
- `Box<dyn SymbolResolver>` / `Box<dyn FormatterOptionsProvider>` -> `std::unique_ptr<...>` (the formatter owns them, `nullptr` = `None`).
  `SymbolResolver::symbol()` returns `std::optional<SymbolResult>`; borrowed strings in it are only valid until the resolver is called
  again, so if the formatter calls the resolver again before it has used a result, it must copy it first (`internal::to_owned()`,
  same as Rust's `to_owned()`).
- `Option<u32>` operand args -> `std::optional<std::uint32_t>`. `Result<Option<T>, IcedError>` -> `Result<std::optional<T>>`.

### Writing a syntax formatter (gas/intel/masm/nasm)

1. Public header `include/iced_x86/<syntax>_formatter.hpp`: `class GasFormatter final : public Formatter` with `GasFormatter()` (Rust
   `new()`) and `GasFormatter(std::unique_ptr<SymbolResolver>, std::unique_ptr<FormatterOptionsProvider>)` (Rust `with_options()`),
   `ICED_X86_FORMATTER_USING_BASE_METHODS;` and `override`s of all pure virtual methods. Implementation: `src/formatter/<syntax>/*.cpp`,
   internal headers: `src/internal/formatter/<syntax>/*.hpp` (namespace `iced_x86::internal::<syntax>`).
2. Instruction tables (Rust `<syntax>/fmt_tbl.rs` + `info.rs`): constant data, see *Formatter tables* below. The generated enums
   (`InstrOpInfoFlags`, `InstrOpKind`, ...) are in `internal/formatter/<syntax>/*.hpp`.
3. Memory size tables (Rust `<syntax>/mem_size_tbl.rs`): `internal/formatter/<syntax>/mem_size_tbl_data.hpp` (generated) has the data
   (`MEM_SIZE_TBL_DATA`, `BCST_TO_DATA`, `SIZES`, shift/mask constants) and the generated `match`es:
   `get_memory_keywords(ac, value)` (intel/masm, returns `FormatterStringSlice`), `get_memory_keyword(c, value)` (nasm),
   `get_bcst_to_string(c, value)` (gas/intel/nasm). The C++ port of the rest of `mem_size_tbl.rs` is the syntax formatter's job.
4. Shared runtime (all in namespace `iced_x86::internal`):

   | Rust | C++ |
   |------|-----|
   | `FormatterString` (`lower`/`upper`, `get(upper)`, `len()`, `is_default()`) | `FormatterString` (`internal/formatter/formatter_string.hpp`): a pointer to constant data, pass it by value |

6. Fast formatter: `SpecializedFormatter<TraitOptions>` is a template (Rust generic), `TraitOptions` derives from
   `SpecializedFormatterTraitOptions` and hides the static constants/functions it wants to change. The library contains the
   non-inline member functions of the `FastFormatter` (`DefaultFastFormatterTraitOptions`) and `DefaultSpecializedFormatterTraitOptions`
   instantiations (`ICED_X86_INTERNAL_INSTANTIATE_SPECIALIZED_FORMATTER(extern, ...)` in the header, the whole class isn't
   instantiated so the inline `std::string` wrapper isn't compiled into the library). **It never allocates memory and doesn't use
   `std::string`/`std::vector`** (embedded use):
   - API: `std::size_t format(const Instruction&, char* output, std::size_t output_size)` (+ `char (&)[N]` overload): writes the
     NUL terminated text, returns its length, `snprintf()` semantics if the buffer is too small (truncated + NUL terminated,
     returns the full length; `output_size == 0`: nothing is written). `MAX_FMT_INSTR_LEN` (Rust's private `MAX_FMT_INSTR_LEN`,
     315) is public: the max length without a symbol resolver. `format(const Instruction&, std::string&)` is a header-only
     convenience wrapper (formats to a stack buffer and appends it; formats again into the string if it's longer, which is
     only possible with long symbols).
   - Fast path (same as Rust which reserves `MAX_FMT_INSTR_LEN` bytes and writes with raw pointers): if
     `output_size > MAX_FMT_INSTR_LEN` and there's no symbol resolver, `format_core()` writes directly to `output` without
     size checks (whole `FastString`s, 4 bytes per 2 hex digits: the writes can go past the end of the text but they always fit in
     `MAX_FMT_INSTR_LEN` bytes; `verify_output_has_enough_bytes_left()` (default `true`) verifies every write against `limit_` and
     aborts if it fails; the tests verify it for all test instructions).
   - Otherwise `format_slow()` (`noinline`) formats to a `MAX_FMT_INSTR_LEN + 1` byte stack buffer (`internal::fast::FastFmtOutput`
     `output_`) and copies it to `output` with truncation (`fast_fmt_append()`/`fast_fmt_finish()`, `src/formatter/fast/fast_formatter.cpp`).
     Symbols can be any length: `write_symbol2()` copies the stack buffer and the symbol text to `output` and continues at the
     start of the stack buffer (Rust: `use_dst_only_now!`/`use_dst_next_p_now!`). The symbol functions are only called if there's a
     symbol resolver, so `output_` is never null there.
   - Far branch + symbol resolver: Rust copies the offset's `SymbolResult` (`to_owned()`, heap) because the selector's resolver call
     can invalidate its borrowed strings. C++ only checks if the offset has a symbol and calls the resolver again for the offset after
     the selector has been written.

### Formatter tables

Rust creates most formatter tables at runtime (`lazy_static!`): one `Box<dyn InstrInfo>` per `Code` value (+ `String`s, the
mnemonics with a size suffix are created with `add_suffix()`), `FormatterString`s with `String`s, register names, pseudo ops, etc.
That's ~450-800 KB of heap memory (~5500 allocations) per formatter. In C++ they're all **constant data** (in `.rodata`, constant
initialized: no heap memory, no startup code, no locks) and the formatters only allocate memory for their own state (the fast
formatter doesn't allocate at all).

- `FormatterString` (`internal/formatter/formatter_string.hpp`) is a pointer to a length byte followed by the lowercase chars and
  the uppercase chars, eg. `"\x03" "add" "ADD"`. `FormatterStringData<N>` creates the data at compile time from a lowercase
  literal (used by the hand written constants, eg. `fmt_consts.cpp`: `ICED_FMT_STR(byte, "byte")`).
- Instruction infos: the generated `src/formatter/<syntax>/fmt_data.cpp` (`internal/formatter/<syntax>/fmt_data.hpp`) has
  `INSTR_INFOS[CODE_ENUM_COUNT]` (one 8-byte `InstrInfo` per `Code`: `InstrInfoKind kind` + `mnemonic`, `arg1`, `arg2`, `arg3`),
  `STRINGS` (all `FormatterString` data of the syntax incl. the suffixed mnemonics; a string is referenced by its u16 offset;
  it's < 64KB so it's also a valid MSVC string literal) and `ARGS` (u16 values: extra data, eg. the cc mnemonics of `Jcc`).
  `get_op_info(options, instruction)` (`src/formatter/<syntax>/fmt_tbl.cpp` or `info.cpp`) switches on the kind and calls
  the `op_info()` method of the kind's class (the Rust `InstrInfo` impls). The classes aren't virtual: they're small views
  created on the stack whose constructor reads the fields from the `InstrInfo`. `InstrOpInfo::mnemonic` is a `FormatterString`.
- Generator: `CppInstrInfoTableGen` (+ `Cpp{Gas,Intel,Masm,Nasm}InstrInfoTableGen`) converts each Rust ctor kind + args to an
  `InstrInfo` (a comment at the top of each `Create()` documents the field layout of each kind). **The layout of a kind must match
  the C++ class constructor.** To add a ctor kind: add the kind to `Kinds` (it's the generated `InstrInfoKind` enum), handle the
  ctor kind in `Create()`, add a class and a `case` to `get_op_info()`.
- Register names: `REGS_TBL` (`src/formatter/regs_tbl_ls.cpp`), gas `ALL_REGISTERS` (`%` prefix, `src/formatter/gas/regs.cpp`),
  nasm `ALL_REGISTERS` (`st0`, `src/formatter/nasm/regs.cpp`), generated by `CppTableGen`.
- `FORMATTER_CONSTANTS`, `ARRAY_CONSTANTS` (`fmt_consts.cpp`), the memory size tables (`<syntax>/mem_size_tbl.cpp`, filled by a
  `constexpr` constructor from the generated data) and the pseudo ops (`pseudo_ops.cpp`, created by a `constexpr` constructor
  from `pseudo_ops_defs.hpp`) are `constexpr`/`ICED_CONSTINIT` objects.
- Fast formatter (Rust `fast/fmt_tbl.rs`, `regs.rs`, `mem_size_tbl.rs`, `pseudo_ops_fast.rs`; declared in the public header
  `iced_x86/internal/fast_fmt.hpp` since the formatter is a template): no pointer tables, a `FastString` is a pointer to a length
  byte followed by at least `SIZE` readable bytes. Generated: `MNEMONICS` (all mnemonics, incl. the `v` prefixed ones, in `Code`
  order of first use + padding), `MNEMONIC_OFFSETS` (u16 offset of each `Code`'s mnemonic) and `CODE_FLAGS` (`FastFmtFlags`)
  (`src/formatter/fast/fmt_data.cpp`, `CppFastFmtTableGen`), `REGISTERS[REGISTER_ENUM_COUNT][1 + 8]` (`src/formatter/fast/regs.cpp`)
  and `MEMORY_SIZES[MEMORY_SIZE_ENUM_COUNT][1 + 16]` (`src/formatter/fast/mem_size_tbl.cpp`) (`CppTableGen`). The pseudo ops are
  created at compile time from `pseudo_ops_defs.hpp` (`FAST_PSEUDO_OPS` in `src/formatter/fast/fast_fmt_tbl.cpp`).

### Generated formatter data

`Formatters/Cpp/CppFormatterTableGenerator.cs` (+ `CppInstrInfoTableGen.cs`, `CppFormatterStrings.cs`) and `CppTableGen.cs` generate
the data of all 5 formatters:

- `src/formatter/fast/fmt_data.cpp` + `src/internal/formatter/fast/fmt_data.hpp`: fast formatter mnemonics + flags (constant tables)
- `src/formatter/<syntax>/fmt_data.cpp` + `src/internal/formatter/<syntax>/fmt_data.hpp` (`internal::<syntax>`): constant instruction
  info tables (gas/intel/masm/nasm, see above)
- `src/internal/formatter/<syntax>/mem_size_tbl_data.hpp` (`internal::<syntax>`, gas/intel/masm/nasm): memory size keywords/broadcast data + `constexpr` lookup functions
- `src/formatter/fast/mem_size_tbl.cpp`, `src/formatter/fast/regs.cpp`: fast formatter memory size keywords and register names
- `src/formatter/regs_tbl_ls.cpp`, `src/formatter/gas/regs.cpp`, `src/formatter/nasm/regs.cpp`: register name `FormatterString` tables
- `src/formatter/fmt_flow_control.cpp`: `internal::get_flow_control()`
- generated regions in `src/internal/formatter/fmt_consts.hpp` and `src/formatter/fmt_consts.cpp` (the keyword constants)

## Tests

- Framework: `tests/test_framework.hpp` (`TEST_CASE("decoder/xxx")`, `CHECK`, `CHECK_EQ`, `REQUIRE`, ...). Tests
  self-register; just add a `.cpp` file under `tests/<component>/`. Test names are `"<component>/<name>"`.
- Test data: `tests/test_utils.hpp` (`get_decoder_unit_tests_dir()`, ...) = `src/UnitTests/Intel/...`.
- Port the Rust tests of your component (`src/rust/iced-x86/src/<component>/tests/**`) completely. When a Rust test
  is data driven (reads `src/UnitTests/Intel/**.txt`), the C++ test must read the same file and check the same things.
- Shared test helpers (string -> enum conversion, test case parsers used by several components) go in
  `tests/test_utils/` (namespace `iced_x86::tests`).
- Build + run:
  ```sh
  cmake -S src/cpp/iced-x86 -B build -G Ninja -DICED_X86_WARNINGS_AS_ERRORS=ON && cmake --build build && ./build/iced_x86_tests [filter]
  ```
