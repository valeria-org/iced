# iced-x86 C++ port: design and conventions

This document is the contract for everyone working on the C++ port. The C++ code is a port of the **Rust**
crate (`src/rust/iced-x86`). When in doubt, do what the Rust code does.

## Goals

- Full feature parity with the Rust crate: decoder, encoder, block encoder, op code info, instruction info,
  gas/intel/masm/nasm/fast formatters, code assembler.
- Runtime performance similar to Rust (same algorithms, same data layout, same table-driven design).
- Usable on embedded devices: CRT exists but **stack size is limited**.
- All tests that the Rust crate runs (shared test data in `src/UnitTests/Intel`) must also run and pass in C++.

## Language / build rules

- C++17, no compiler extensions required. Must compile warning-free with GCC and Clang (`-Wall -Wextra -Wshadow=local`), should compile with MSVC.
- The library must compile with `-fno-exceptions -fno-rtti` (this is the default CMake config). No `throw`, `try`,
  `dynamic_cast`, `typeid`. Errors are returned with `iced_x86::Result<T>` / `iced_x86::IcedError` (`include/iced_x86/iced_error.hpp`),
  which mirror Rust's `Result<T, IcedError>`. Where Rust panics (`iced_assert!`, `unreachable!`, index out of bounds on
  internal tables) use `ICED_ASSERT(x)`, `ICED_UNREACHABLE()`, `ICED_DEBUG_ASSERT(x)` from `src/internal/iced_assert.hpp`.
- **Stack**: no recursion, no VLAs/`alloca`, no big local arrays or big structs on the stack. The build warns if a frame
  is larger than 1024 bytes (`-Wframe-larger-than=1024`); fix any such warning. Big tables are `static const` data.
- **No dynamic initialization at namespace scope** in the library (no global objects with constructors, no static
  registration). Tables that Rust builds lazily (`lazy_static!`) are built lazily in C++ too, using a function-local
  `static` (thread-safe init), eg. `static const Foo& get_foo() { static const Foo foo = create_foo(); return foo; }`.
  Plain constant data (`static const std::uint8_t DATA[] = {...}`, `constexpr` arrays) is fine.
- Heap usage: std::string/std::vector are allowed (Rust uses `String`/`Vec` in the same places). Don't allocate in hot
  paths where Rust doesn't (eg. the decoder never allocates, the formatter only appends to the output).
- The library is a static library; the linker only pulls in the object files that are used, so keep each component in
  its own `.cpp` files so eg. an app that only decodes doesn't link the formatters.
- Use `std::uint32_t` etc. (`<cstdint>`), `std::size_t`. Use `std::string_view` for non-owning strings passed to/from the API.
- Formatting: tabs for indentation (like the Rust/C# code), `{` on the same line.
- Don't use `<iostream>` in the library.

## Directory layout (`src/cpp/iced-x86`)

```
CMakeLists.txt               GLOB_RECURSE picks up all src/**/*.cpp and tests/**/*.cpp automatically
include/iced_x86/*.hpp       Public API (namespace iced_x86). Generated enums + hand written headers.
include/iced_x86/code_asm/   Public code assembler API (namespace iced_x86::code_asm)
src/*.cpp                    Core (Instruction, Register/Code/MemorySize helpers, ...)
src/<component>/*.cpp        Components: decoder, encoder, block_encoder, info, formatter, formatter/{gas,intel,masm,nasm,fast}, code_asm
src/generated/               Generated .cpp files that don't belong to a component (eg. enum_names.cpp)
src/internal/**/*.hpp        Internal headers (namespace iced_x86::internal[::gas|intel|masm|nasm|fast]).
                             Generated internal enums also live here, eg. src/internal/decoder/op_size.hpp
tests/                       Unit tests (namespace iced_x86::tests), one sub dir per component: tests/decoder/...
tests/generated/             Generated test files
bench/                       Benchmarks
```

Include paths: `include/` (public: `#include "iced_x86/instruction.hpp"`) and `src/` (internal:
`#include "internal/decoder/op_size.hpp"`). Tests also have `tests/` in the include path.

Generated files start with `// ⚠️This file was generated by GENERATOR!🦹‍♂️` and must never be edited by hand; change
the generator instead. Hand written files may contain generated regions (`// GENERATOR-BEGIN: Id` ...
`// GENERATOR-END: Id`) written by `FileUpdater`, same as the other languages. Prefer whole generated files.

## Generator

The generator is `src/csharp/Intel/Generator` (C#, .NET 10: `~/.dotnet/dotnet`). C++ support: `TargetLanguage.Cpp`,
`CppConstants` (paths/helpers), `CppIdentifierConverter`, `Documentation/Cpp/*`, `Constants/Cpp/*`, `Enums/Cpp/*`.
Put new C++ generators next to the Rust ones in a `Cpp` sub dir (eg. `Decoder/Cpp/CppDecoderTableGenerator.cs`) and
mark them with `[Generator(TargetLanguage.Cpp)]` (they're discovered by reflection). Usually the Rust generator is the
best starting point: the serialized tables are language independent, only the syntax differs.

```sh
cd src/csharp/Intel/Generator
~/.dotnet/dotnet run -c Release -- -l cpp     # only generate C++ files
~/.dotnet/dotnet run -c Release               # all languages: must not change any non-C++ file (check with git status)
```

`CppEnumsGenerator` generates *all* enums (also the ones generated by other generators, eg. the encoder/instr info
generators create a `CppEnumsGenerator` and call `Generate(enumType)`). `GetIncludePath(typeId)` returns an enum's include path.

## Naming (mirror the Rust API)

| Rust | C++ |
|------|-----|
| `enum Code { Add_rm8_r8, .. }` | `enum class Code : std::uint16_t { Add_rm8_r8 = 5, .. }` (generated) |
| `struct DecoderOptions; impl DecoderOptions { pub const NONE: u32 }` (flags) | `struct DecoderOptions { static constexpr std::uint32_t NONE = 0; };` (generated) |
| `Debug`/`Display` of a public enum | `const char* to_string(Code)` (generated, `src/generated/enum_names.cpp`) |
| `IcedConstants::CODE_ENUM_COUNT` | `iced_x86::IcedConstants::CODE_ENUM_COUNT` (public, generated) |
| struct `Instruction`, `Decoder`, `Encoder`, `BlockEncoder`, `InstructionInfoFactory`, `OpCodeInfo`, `GasFormatter`, `FormatterOptions`, ... | same type names (PascalCase) |
| method `instr.op0_kind()`, `instr.set_op0_kind(k)` | same names, snake_case: `instr.op0_kind()`, `instr.set_op0_kind(k)` |
| associated fn `Decoder::with_ip(..)`, `Instruction::with2(..)` | `static` member function with the same name |
| methods on enums: `reg.size()`, `code.mnemonic()`, `mem_size.info()`, `cc.xxx()` | free functions in a `<snake_type>_ext` namespace: `register_ext::size(reg)`, `code_ext::mnemonic(code)`, `memory_size_ext::info(ms)` (header: `include/iced_x86/<snake_type>_ext.hpp`) |
| `pub(crate)` items | `iced_x86::internal` (in `src/internal/**`) |
| `Result<T, IcedError>` | `iced_x86::Result<T>` |
| `Option<T>` | `std::optional<T>` (or a pointer for optional references) |
| `&[u8]` | `const std::uint8_t* data, std::size_t size` (+ convenience overloads, eg. `std::vector<std::uint8_t>`) |
| returned `&'static [T]` (eg. `cpuid_features()`) | `iced_x86::Slice<T>` (`include/iced_x86/slice.hpp`) |
| `&str` / `String` | `std::string_view` / `std::string` |
| trait objects (`Box<dyn SymbolResolver>`, `dyn FormatterOutput`) | abstract classes with virtual functions |
| `impl Iterator` | C++ iterators (`begin()`/`end()`) where it makes sense |
| C++ keyword clash (`and`, `or`, `not`, `xor`, `int`, `default`, ...) | append `_`: `and_`, `int_` (same as `CppIdentifierConverter.Escape`) |

Where Rust uses generic `with2<T, U>(code, op0: T, op1: U)` taking `Register`/`i32`/`u32`/`i64`/`u64`/`MemoryOperand`,
C++ uses overloads with the same name.

## Public headers

Public headers (`include/**`) can't include internal headers (`src/internal/**`, not installed). Use `assert()`
(`<cassert>`) for debug asserts in inline public code and `std::abort()` instead of `ICED_ASSERT()`.
Internal tables used by inline public functions are declared `extern` in the public header in `namespace iced_x86::internal`.

## Instruction

`Instruction` (include/iced_x86/instruction.hpp) has exactly the same layout as Rust's (40 bytes, same fields, same
bit packing in `flags1`, etc.). Its data members are private; internal code that needs raw access uses
`iced_x86::internal::InstructionInternal` (a `friend` struct with static functions, the equivalent of Rust's
`instruction_internal.rs`, in `src/internal/instruction_internal.hpp`). Hot getters/setters are inline in the header.

## Decoder

`Decoder` (include/iced_x86/decoder.hpp): `Decoder(bitness, data, size, options)` (Rust `new`), `Decoder::with_ip(bitness, data, size, ip, options)`,
`Decoder::try_new(...)`/`try_with_ip(...)` return `Result<Decoder>`; `std::vector<std::uint8_t>` overloads exist (the decoder never
owns/copies the data). `decode()`, `decode_out(Instruction&)`, `for (const Instruction& instr : decoder)` (range-for, decodes into the
iterator's instruction). Decoder test cases (used by the encoder/formatter/instr info tests): `tests/test_utils/decoder_test_utils.hpp`
(`decoder_tests(include_other_tests, include_invalid)`, `encoder_tests(...)`, `get_test_cases(bitness)`, `create_decoder(...)`, ...).
Rust `#[should_panic]` tests: `aborts([] { ... })` in `tests/test_utils/abort_utils.hpp`.

## Code assembler

`iced_x86::code_asm` (`include/iced_x86/code_asm.hpp`). `CodeAssembler a(64);` (or `CodeAssembler::create(64)` -> `Result`).
Instruction methods are overloads (Rust traits/generics), C++ keywords get a `_` suffix (`a.xor_(rcx, rdx)`, `a.int_(3)`).
Instruction/prefix/label/data methods return `CodeAssembler&` and errors are *sticky*: the first error is stored
(`has_error()`, `error()`, `clear_error()`), later calls are ignored and `assemble()`/`assemble_options()` fail with it.
Methods that return a value in Rust return `Result<T>` (`bwd()`, `fwd()`, `CodeAssemblerResult::label_ip()`).
Registers are `constexpr` constants (`rax`, `xmm0.k1().z()`), memory operands: `dword_ptr(rax + rcx * 4 + 8).fs()`.
The generated instruction methods are declared in several base classes (`code_assembler_fns.hpp`, GCC is quadratic in the
number of class members) and implemented in `src/code_asm/fn_asm_impl_N.cpp`.

## Tests

- Framework: `tests/test_framework.hpp` (`TEST_CASE("decoder/xxx")`, `CHECK`, `CHECK_EQ`, `REQUIRE`, ...). Tests
  self-register; just add a `.cpp` file under `tests/<component>/`. Test names are `"<component>/<name>"`.
- Test data: `tests/test_utils.hpp` (`get_decoder_unit_tests_dir()`, ...) = `src/UnitTests/Intel/...`.
- Port the Rust tests of your component (`src/rust/iced-x86/src/<component>/tests/**`) completely. When a Rust test
  is data driven (reads `src/UnitTests/Intel/**.txt`), the C++ test must read the same file and check the same things.
- Shared test helpers (string -> enum conversion, test case parsers used by several components) go in
  `tests/test_utils/` (namespace `iced_x86::tests`).
- Build + run:
  ```sh
  cmake -S src/cpp/iced-x86 -B build -G Ninja -DICED_X86_WARNINGS_AS_ERRORS=ON && cmake --build build && ./build/iced_x86_tests [filter]
  ```

## Documentation

Public API gets doc comments (`///`), ported from the Rust doc comments (adapted to C++ names). Internal code only
needs comments where Rust has them.
